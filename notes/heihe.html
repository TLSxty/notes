黑盒行为的归因与验证

出事之后怎么定位：从可重放样本到判别实验　·　方法论 · 公开版

一句话：先让失败可重放，再一次只动一个维度地逼问，最后用「竞争解释预测相反」的判别实验定案。

本文只写方法。具体某次排障的结论写在该问题的专题笔记里（如 上游渠道校验排障）， 因为结论有时效性，方法没有。

零、证据分级（先声明，再动笔）

任何一份排障记录，开头就该把证据分成三档，读者才知道哪句能信到什么程度：

档 含义 判据
A · 已确证 可复现的对照实验结果 有脚本、有输入、有输出，别人重跑能得同样结果
B · 机制已确证 读过实现层（字节码 / 源码 / 日志）而非靠名字猜 能指出具体方法、具体字段、具体日志行
C · 未确证 只是候选解释 必须标出来，并给出判别实验设计

C 档不是耻辱，隐瞒 C 档才是。在 C 档没升级到 A/B 之前不要改代码 —— 改错方向的代价远高于多跑一轮实验。 D:\项目 Bmod\docs\YSM渲染破坏问题分析.md 是这个写法的完整实例：它 §五 留了四条候选机制全部标为未确证， 正因为没定案，所以没有直接动代码。

一、前提：先把失败变成可重放的样本

没有稳定复现，后面所有方法都无从谈起。三件事：

  1. 留存失败输入本身，不只是留「失败了」这个事实。落盘原始请求体 / 原始日志 / 原始崩溃栈。
  2. 永不自动清理失败样本。成功样本可以只留最近 N 份，失败样本一份都不能丢。
  3. 建一条绕过主程序的直连重放通道（直连上游 API、直接调那个方法、直接 javap 那个类）， 让你能任意变形输入再发一次。

反面实例（真踩过）：早期把请求体落在「只保留 20 份」的滚动目录里，失败体被后续成功请求冲掉， 无法重放，只能改用「把失败内容拼成 user 消息」的替代实验 —— 这一拼同时引入了双空格和 role 变化 两个额外变量，于是得出了完全错误的结论，并且这个错结论又活了 6 天。 修复方式：失败体单独落 rejected/ 目录，永不清理。

判据：能不能用一条命令，把「昨天那次失败」原样再打一次并且再失败一次？不能，就先修这个。

二、分维排除：先砍掉大面

拿到可重放样本后，不要急着读内容。先按「输入被切成哪几个正交维度」逐个排除：

header / 传输参数 / 体积与结构 / 内容本体 / 环境（凭证、域名、版本）

每次只动一个维度，其余保持原样。

  • 一整轮 header 对照（补官方头、去自定义头、换 UA）全放行 → header 维度出局，不用再想。
  • 参数维度（max_tokens、reasoning_effort、prompt_cache_key、stream_options）逐个删改仍失败 → 出局。
  • 体积维度（截断消息数、删光 tools）仍失败 → 出局。
  • 最后只剩「内容本体」，而且只有把整个内容换成一个极简替身才通过 —— 这就把范围锁死在内容里了。

这一步的价值不在找到原因，而在写出「已排除」清单。清单本身能阻止下一个人（或压缩后的自己） 重走一遍同样的弯路。专题笔记里应该有一节专门叫「已排除的维度」。

三、二分：从整块缩到一串字符

范围锁进内容后，用二分把定位粒度一级级压下去。典型三级：

  1. 块级二分：内容截前 N 行/前 N 条，找「通过 / 不通过」的分界。O(log n) 次请求。
  2. 句级二分：把分界那一行按句子拆开，逐句、逐前缀组合测。 常见结果是需要两句共现才触发 —— 单句都放行。
  3. 词级 / 字符级：在触发区间内做最小改动，确认锚点到底卡在哪几个字符上。

关键技巧：先解除旧假设的掩蔽。 第二次排同一个问题时，旧补丁已经把「上次那个触发点」改掉了，于是新触发点被它盖住： 直接二分会在旧位置附近反复横跳。正确做法是先手工把旧补丁的改动还原/绕过，再做二分。 实例：10-27 那轮把第 35 行整行删掉之后再做前缀二分，分界才从「34/35」跳到「4/5」， 新的触发点才暴露出来。

四、判别实验：区分「字面匹配」与「语义判断」

这是整套方法里最值钱的一步。二分只能告诉你「哪里敏感」，判别实验才能告诉你「对方是怎么判的」。

通式：要证明机制 M，必须找一个「M 预测会变、而竞争解释预测不变」的观察。

两种竞争解释的对照设计：

想区分 实验 A（M 预测变） 实验 B（竞争解释预测不变）
字面连续匹配 vs 语义近似匹配 在锚定区间内改空白/插字符 → 若变，说明是字面 在锚定区间外改实词 → 若不变，说明不看语义
单点触发 vs 两句共现 只放句 0 只放句 1
位置敏感 vs 全文敏感 换顺序 移到别处

反面实例（真踩过）：第一轮只测了「改实词 → 通过」，就断言「网关在归一化空间做近似匹配」。 这个结论能解释当时全部数据，但它是过度概括 —— 少做实验 B。 补上实验 B 后（把锚定区间外的一个 or 改成 and）结果仍然失败， 于是「字面连续匹配」这个更简单的解释胜出，前面那个复杂假设被推翻。

教训一句话：「改 A 有效」不等于「A 的语义被理解了」。 必须再测一个「不该有效却有效」的对照。

五、修法取舍：优先不改变语义的表征层改动

定位到锚定串之后，能绕过去的方法往往有一堆。选哪个？

优先级 类型 例 理由
高 表征层：空白、换行、分隔符、零宽字符 句号后换行；句间空格 → 换行 物理切断锚定串，确定性生效；且不改变提示语义
中 局部措辞替换 Web GUI → web interface 能否绕过取决于锚定串有没有被碰到，概率性生效
低 整段删除 删掉整段运行时提示 生效但丢信息，且上游改措辞后会再犯

反面实例：同一轮里 or→and（措辞层）没绕过，而改空白（表征层）全部绕过。 措辞改动看起来更「干净」，实际不可靠。

表征层改动必须可度量，否则你不知道自己改了多少东西：

原内容: 17104 字 / 106 行
改写后: 17104 字 / 193 行
非空白字符完全一致: true     幂等: true
替换命中数: 87

三条硬指标：非空白字符零变化（语义不变）、幂等（跑两次等于跑一次）、命中数可数（改动范围可审计）。

六、结论必须自带失效判据

如果结论依赖「对方现在的行为」，它一定会过期。过期不可怕，不知道它过期了才可怕。

每篇这类笔记的 frontmatter 必须有两个字段：

  • verify-script: —— 一条命令，重跑就能验证结论是否仍成立。
  • recall-trigger: —— 什么现象出现时应该回来重跑它。

验证脚本要验「在用的那份代码」，不要验复制品。 做法：从真实源文件里按大括号切出函数、 拼成临时模块执行，再对真实端点打一次。这样补丁被改坏、被回退、被升级覆盖，脚本都会报出来。

判据要写成「基准值应该是什么」，例如「未打补丁时这一行应当是 400」—— 如果某天它变成 200，说明规则已变，补丁可以删。验证通过 ≠ 结论仍有效， 要验证的是「结论的前提仍成立」。

七、反模式清单（都是真踩过的）

反模式 现场 正确做法
差异当原因 把「失败侧与正常侧只有第 3 行不同」当根因，实际那是两侧本来就跑不同模型 差异只是线索；要证明它，得改掉它看是否恢复
只测「改 A 有效」 据此断言机制，6 天后被推翻 补一个「不该有效却有效」的对照
样本留存太少 失败体被滚动冲掉，无法重放 失败样本永不清理
拼装体做实验 拼成 user 消息，引入双空格 + role 两个变量 只在原始样本上做单变量变形
凭名字推行为 「从类名反推行为」是 MC 侧两处错误的共同成因（应力网络、旋转表示） 反编译 / javap -c 核实之前，类名与字段名只能当线索
信崩溃报告的 Suspected Mods Mixin 失败是惰性的，首次触碰目标类才炸，报错指向无关模组 在 latest.log 里搜 Mixin apply failed
只测一层就下结论 「槽位搬运无类型校验」成立但「槽位 mayPlace 有判据」不成立 同一系统的不同层次判据不同，每层分别验证
凭先验推测缺陷 曾误报 4 处坐标颠倒，逐行对照后证实并不存在 坐标/公式类结论必须 grep 或逐行对照源码
把未触发的隐患当根因 某处缺 try/finally 是真实字节码事实，但本次并未触发 明确写「本次未触发，不是根因」

九、一页速查

1. 可重放？     不能 → 先落盘失败样本 + 建直连通道（永不清理失败样本）
2. 砍大面       按 header / 参数 / 体积 / 内容逐维排除，一次只动一维 → 写「已排除」清单
3. 二分         块级 → 句级 → 词级；先解除旧补丁的掩蔽再二分
4. 判别实验     找一个「我的解释预测会变、竞争解释预测不变」的观察 → 才能定案
5. 修法         优先表征层（空白/分隔符），它确定性生效且不改语义；措辞替换是概率性的
6. 度量         非空白字符零变化 + 幂等 + 命中数可数
7. 交付         带 verify-script + recall-trigger；验证的是「前提仍成立」，不是「曾经修好过」
