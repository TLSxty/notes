参考实现的契约提取

动手之前怎么不漏：复位者判据与性质测试　·　方法论 · 公开版

一句话：参考代码的价值不在「长什么样」，在「它靠什么保证了什么」。 抄结构会漏掉求值位置，抄契约才不会。

本文与 黑盒行为的归因与验证 是同一族方法的两个方向：那篇讲出事之后怎么定位，这篇讲动手之前怎么不漏。

零、问题形态：结构相同，语义相反

真实踩坑（项目 B）：参照已有的冻结实现写了新的冻结机制，字段名、方法名、结构几乎一一对应，但漏掉了唯一实质差异——时间戳在什么时刻被求值。

// 参考实现：时间戳在「读」的时候求值
public static boolean isFrozen() {
    return pendingUuid != null && Util.getMillis() < freezeUntilMillis;
}

// 自己的实现：时间戳在「写」的时候求值（在 tickServer 里）
Long deadline = DEADLINE.get(id);
if (deadline == null || now < deadline) continue;
resolveTimeout(player, killerId);   // ← 顺手把 WAITING 里的条目 remove 了

后果链：

tickServer 不跑 → WAITING 永不为空 → blocksWorldTick() 恒 true → 世界永久冻结

而参考实现在同样条件下照样解冻，因为没有任何驱动者，也就没有「驱动停摆」这回事。

两段代码字段名一样、方法名一样、连注释都可能一样。差异不在字面上，所以「照着参考写」这句话在字面上无法约束它。

本例取自用户提供的代码片段与结论；本机未定位到 我方实现 源文件（D:\项目 Bmod 下 grep 无命中），此处只按片段语义分析，不主张对文件内容的其它推断。

一、复位者判据（本方法的核心）

对每一个可变状态问一句：谁负责把它复位？

答案只有三种，风险截然不同：

复位者 性质 风险
读时按时间戳 / 条件算出来 惰性、自愈 无。没有驱动者，就没有驱动停摆
定时器 / tick / 事件处理器 急切 驱动一停 → 永久卡死
永不复位（只增不减） 泄漏 迟早出事

上例：isFrozen() 属于第一类（读时算），WAITING 集合属于第二类（靠 tickServer 主动 remove）。结构一样，复位者不同，语义就相反。

可执行的判别问题

把这个驱动整个注释掉，这个性质还成立吗？

实现 注释掉 tickServer 后 判定
参考实现 照样解冻 自愈，安全
我方实现 永久冻结 驱动依赖，必须显式设计

这个问题不需要读完整个文件，问一句就能把两类分开。它是黑盒行为的归因与验证 §四 判别实验的一个具体形态——「找一个两类机制预测不同的观察」，这里那个观察就是不跑驱动。

二、契约表（写第一行实现代码前填完）

# 项 参考实现 我的实现 有意差异？
1 可变状态清单
2 每个状态的复位者（读时 / 驱动 / 永不）
3 参考实现保证的性质，写成「即使 X 不发生，Y 仍成立」
4 判据位置：准入判断读的是哪个字段 / 哪个方法
5 幂等性与可重入性（同一输入来两次会怎样）
6 最坏情况（参考实现被逼到极限时的行为）

三条使用规则：

  1. 「有意差异」列只许填「有意」或「未察觉」，不许填「无差异」。 填「无差异」说明没找——一定存在差异，因为你的场景不同。
  2. 任何一行填不出来 → 停下来问 / 去读源码，不要边写边补。 边写边补的表一定是照着实现倒推的，等于没做。
  3. 第 3 行的写法是硬约束：必须是可判定的断言，不能是「它会正常工作」这类描述。「即使 X 不发生，Y 仍成立」这个句式会强迫你说出依赖关系。

上表是最小版（6 行，只覆盖状态与生命周期）。实际动手时用可打勾的完整版：参考契约八维度清单（8 个跨语言恒真维度，含反向验证法与「踩新坑加一行」的维护规则）。

三、性质先落成测试，再写实现

这是唯一能把契约钉死的机制：文字描述会被忽略，测试不会。

// 不跑任何 tick，只推进时钟，然后断言已解冻
assertFalse(isFrozenAt(now + FREEZE_MS + 1));

规则：

  • 第 3 行的每条性质 → 一条可执行断言。
  • 至少一条必须让驱动循环完全不跑（否则测不出复位者类别）。
  • 顺序必须是「先写参考实现的性质测试 → 再写自己的实现」。实现完再补测试，人会照着实现写，测试退化成同义反复。
  • 测试名里带上性质，不要叫 testFreeze()，要叫 freeze_expiresWithoutTick()。

四、自有代码与他人代码：两种不同陷阱

用户明确区分过这两类参考源，对策不同：

参考源 陷阱 对策
我们自己的代码 假熟悉：「我写的，我知道它干什么」→ 跳过重读，凭记忆抄 必须重新打开实际文件；优先查「上次为什么改过这里」（git log / docs/已验证结论.md），改过的位置往往就是当年的坑
他人的代码 结构匹配：照形状抄，不懂它的边界条件 必须先回答「它靠什么保证行为」，再动笔；它的命名与注释是线索不是事实（同 1.18.2 Forge API 事实速查 §九「不凭方法名推测行为」）

自有代码这一行尤其反直觉：越熟越容易漏，因为熟悉感替代了阅读。上例正是自有代码之间的参照。

五、反模式

反模式 为什么没用
「你仔细一点 / 认真读参考代码」 这是要求不是机制，没有可执行内容，也没法检查是否做到
给参考代码加更多注释 注释写的是「这段在干什么」，而漏掉的是「性质靠什么成立」——两回事
把参考代码全文贴进去当模板 贴得越多越容易被当模板，结构相似度反而变成干扰项
实现完再补测试 补出来的测试照着实现写，测不出漏点
把「结构相同」当「语义相同」 上例就是结构相同、语义相反的完整反例
差异清单里写「无差异」 说明根本没找；必须写「有意」或「未察觉」

六、一页速查

1. 复位者     每个可变状态谁复位？读时算 / 驱动推 / 永不
2. 最坏情况   把驱动整个删掉，性质还成立吗？不成立 → 驱动依赖，必须显式设计
3. 契约表     性质写成「即使 X 不发生，Y 仍成立」；差异必须标「有意 / 未察觉」
4. 先测试     一条「驱动完全不跑也成立」的断言，写在实现之前
5. 交付       差异清单随代码一起留下，不要只活在对话里
